- Quote calculator rates, area limits and the official WhatsApp link live only in `src/lib/cotizador.ts` (tested in `cotizador.test.ts`); UI in `src/components/cotizador/` — keeps prices consistent in one place.
- Logistics zones, percentage bounds and surcharge calculations also live in `src/lib/cotizador.ts`; a dedicated calculator section shows base, surcharge and total separately so base construction rates remain unchanged.
- Both construction systems use the shared SYSTEMS configuration and parameterized calculator components; retain independent per-system areas/sync and a shared logistics selection to preserve values when switching tabs.
- Calculator WhatsApp links use the site's existing direct contact with encoded shared summaries; keep the official business short link available because short-message links do not reliably support dynamic prefills.
- FAQ content uses typed blocks in `src/data/faqs.ts`, shared by the UI and plain-text FAQPage JSON-LD; keep FAQ interaction and scoped motion in its own component to avoid changing existing sections.
- Service pages (/woodframe, /construccion-tradicional, /mobiliario) share `ServicePage` and `src/data/servicios.ts`, read prices/logistics from `cotizador.ts`, and are prerendered via vite.config pages — keeps one price source and text in initial HTML.
- The cabin configurator is a lazy client-only module in `src/components/configurator`, backed by the scoped Zustand store and pure validation helpers in `src/store/useConfigurator.ts`; procedural meter-based geometry and local canvas textures avoid external model dependencies and keep the existing calculator available on WebGL failure.

- The editor uses a common metric polygon as area authority, a pure planar half-edge geometry module, Immer patch history, validated compressed URL designs and guarded browser storage; this keeps price, undo and shared designs consistent without touching the classic calculator.
- Procedural PBR bundles live in a WeakMap keyed by Texture and are linked explicitly to clones; three.js userData cloning serializes textures and destroys their runtime matrices.
- Complex gable roofs use the clipped upper envelope of overlapping rectangular tents; shared affine faces keep ridge and valley heights continuous and limit gable infill to the footprint boundary.
- The room program (living zone + back strip of baths/bedrooms with fixtures) is generated by `suggestedLayout`/`roomProgram` in `src/store/useConfigurator.ts`; fixtures are separate from counters so furniture stays movable without changing counter pricing/validation.
- Exterior/interior wall editing uses the SVG metric `PlanEditor` and pure `wallEditing` helpers; all committed changes use the existing store history and validation, while shape replacement requires confirmation because it regenerates the room program.
- Canvas context-loss listeners must be removed on viewer unmount and ignore detached canvases; intentional renderer disposal when switching to the plan is not a device failure.
- Interior camera presets fit the footprint center and active floor using viewport aspect; zoom buttons manipulate OrbitControls distance so wheel, pinch, and buttons share camera limits.
- Architectural proposals are explicit dimensioned room boxes in `src/config/layoutProposals.ts` (data only, never imports the store); `buildLayoutProposal` lives in `src/store/useConfigurator.ts` because the store builds its own first design while loading — a module the store imports must never import the store back, since Vite turns imports into namespace lookups that are only ready after a module body runs.
- Gallery application of a proposal merges shared wall runs, validates every opening against the resulting walls, and replaces the footprint/program only after confirmation, using the existing history and persistence.
- Interior stairs are placed by `findStairSpot`/`stairConflict` in `src/store/useConfigurator.ts` (walls, furniture, other stairs and slab holes checked); multi-floor room programs reserve a stair bay and floor changes relocate or regenerate so every level keeps a valid stair; a spiral type covers small footprints.
- The AI stair assistant calls the Gateway only from the `reviewStairs` server function; every AI proposal passes through `resolveProposal` (stairConflict + findStairSpot) before applying, so the model can never place an invalid stair.
- Interior stairs rotate freely via the 3D `StairRotateHandle` (5° snap, Shift 1°); commits go through `editStair` validation so invalid angles revert.
- `/sitemap.xml` is generated from each route's required `staticData.sitemap` decision via `src/lib/sitemap.ts`; new routes must declare inclusion so the sitemap follows the router without a manual URL list.
